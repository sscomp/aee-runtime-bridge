# AEE-5 Runtime Registry — Configuration

**Version:** 1.0
**Date:** 2026-07-10

AEE-5 introduces a YAML configuration file that
describes the Runtime Registry. The file is optional;
a fresh bridge works with sensible defaults (just the
built-in `aee-lightweight-local` Runtime).

The file is loaded once at app startup, from the path
in the `AEE_RUNTIME_CONFIG` env var. If the env var is
unset, AEE-5 uses only the built-in Runtime and the
operator can register additional Runtimes via the
`POST /v1/runtimes` API.

---

## 1. Schema

```yaml
# runtimes.yaml — AEE-5 Runtime Registry configuration.
#
# The bridge reads this at startup if AEE_RUNTIME_CONFIG
# points at it. The file is optional. Defaults:
#   auto_register_builtin: true
#   default_runtime_id: aee-lightweight-local
#   allow_unknown_health: true

runtimes:
  # Whether to auto-register the built-in
  # `aee-lightweight-local` Runtime at startup.
  # Default: true.
  auto_register_builtin: true

  # The id under which the built-in is registered.
  # Default: aee-lightweight-local. The build-in
  # descriptor is rewritten to use this id; the old
  # id is NOT also present.
  default_runtime_id: aee-lightweight-local

  # Whether the selector should treat `unknown` health
  # as dispatchable. Default: true (AEE-4 compat).
  # When false, Runtimes that have never reported
  # health are excluded from candidacy.
  allow_unknown_health: true

  # User-defined Runtime descriptors. Each becomes
  # a row in the `runtimes` table on startup. The
  # config file is the source of truth — a later
  # operator who edits the YAML expects their
  # change to take effect at next start.
  definitions:
    - runtime_id: r-shell-prod-01
      runtime_type: shell
      display_name: Production shell runtime
      version: "1.0.0"
      enabled: true
      endpoint: "http://shell.example.invalid:9000"
      capabilities:
        - task.shell
        - task.git
      labels:
        environment: production
        trust_level: external
      limits:
        max_concurrency: 8
        timeout_seconds: 900
      health:
        status: unknown

    # Another Runtime example.
    - runtime_id: r-claude-code-01
      runtime_type: claude_code
      display_name: Claude Code runtime
      capabilities:
        - task.shell
        - task.claude_code
      labels:
        environment: sandbox
      limits:
        max_concurrency: 1
        timeout_seconds: 3600
```

The full field reference is the same as the
`RuntimeDescriptor` dataclass in
`aee.runtimes.models` — see the architecture document
for the type / semantics of each field.

## 2. Env var references

The loader supports two secret-reference conventions:

* **`${VAR}`** — substituted from `os.environ` at load.
  Used in any string field.
* **`env:VAR`** — same as `${VAR}` but in any value
  position.

```yaml
runtimes:
  definitions:
    - runtime_id: r-shell-01
      runtime_type: shell
      endpoint: ${SHELL_RUNTIME_ENDPOINT}    # expanded from env
      # OR:
      endpoint: "env:SHELL_RUNTIME_ENDPOINT"
```

A reference to an undefined env var is a **fail-fast**
error: the bridge refuses to start with a
partially-resolved config. The operator sees a clear
`RuntimeConfigError` in the bridge's stderr log.

The loader only resolves env refs in `endpoint`,
`version`, and `display_name` (i.e. descriptive
fields). It deliberately does NOT resolve them in
`runtime_id` (the primary key must be deterministic
and config-only).

## 3. Loading the config

```bash
# 1. Set the env var.
export AEE_RUNTIME_CONFIG=/etc/aee/runtimes.yaml

# 2. Set the API key (same as AEE-1).
export BRIDGE_API_KEY=...

# 3. Start the bridge.
.venv/bin/python app.py
```

A malformed YAML file aborts startup with a clear
`RuntimeConfigError`. The full error message includes
the file path and the field that failed validation.

If the file is missing (`AEE_RUNTIME_CONFIG` points
at a non-existent path), startup aborts with
`FileNotFoundError`. The operator should either unset
the env var or fix the path.

## 4. Built-in Runtime

The built-in `aee-lightweight-local` Runtime is
registered automatically at startup if
`auto_register_builtin: true` (the default). The
descriptor:

* `runtime_id` = `default_runtime_id` (configurable).
* `runtime_type` = `aee_lightweight`.
* `capabilities` = `[runtime.aee_runtime, task.shell, task.python, task.git, task.filesystem]`.
* `labels` = `{environment: local, trust_level: internal}`.
* `limits` = `{max_concurrency: 2, timeout_seconds: 1800}`.
* `health` = `{status: unknown, last_checked_at: null}`.

The descriptor is generated by
`aee.runtimes.builtins.aee_lightweight.build_default_descriptor()`.
The full source is in
`aee/runtimes/builtins/aee_lightweight.py`.

If you want to *override* the built-in (e.g. add
labels), register a Runtime with the same
`runtime_id` in the `definitions` list — the config
file is authoritative (`replace=True` semantics):

```yaml
runtimes:
  default_runtime_id: aee-lightweight-local
  definitions:
    - runtime_id: aee-lightweight-local
      runtime_type: aee_lightweight
      display_name: AEE Lightweight (renamed)
      capabilities:
        - runtime.aee_runtime
        - task.shell
        - task.python
      labels:
        environment: local
        trust_level: internal
        region: ap-northeast-1
      limits:
        max_concurrency: 4
        timeout_seconds: 1800
```

The operator-set version of the descriptor wins (it
is applied after the built-in registration, with
`replace=True`).

## 5. Validation rules

The loader validates the file at startup. The
following rules apply (per the AEE-5 task spec §4.2 +
§6):

* `runtime_id` must be a non-empty string.
* `runtime_type` must be a non-empty string.
* `capabilities` must be a list of strings.
* `labels` must be a dict; values are coerced to
  strings.
* `limits.max_concurrency >= 1`.
* `limits.timeout_seconds >= 1`.
* `health.status` must be one of
  `{unknown, healthy, degraded, unhealthy, offline}`.
* `enabled` must be a boolean (or a string that
  parses as one: `1`, `true`, `yes`, `y`, `on`,
  case-insensitive).

A validation failure aborts startup with a
`RuntimeValidationError` message naming the field
that failed.

## 6. Runtime management via the API

The `runtimes.yaml` is loaded **once at startup**.
For per-Runtime changes after startup, use the AEE-5
admin API:

* `POST /v1/runtimes` — register a new Runtime.
* `PATCH /v1/runtimes/{id}` — partial update.
* `POST /v1/runtimes/{id}/enable` / `/disable` —
  flip the flag.
* `PATCH /v1/runtimes/{id}/health` — set health
  status (e.g. after a probe).

The API is the recommended path for ad-hoc changes.
A restart with an updated YAML is the recommended
path for permanent, version-controlled changes.

## 7. Example: dual-runtime setup

```yaml
# runtimes.yaml — one built-in (AEE Lightweight)
# + one user-defined Shell runtime.
runtimes:
  auto_register_builtin: true
  default_runtime_id: aee-lightweight-local

  definitions:
    - runtime_id: r-shell-prod-01
      runtime_type: shell
      display_name: Production shell runtime
      capabilities:
        - task.shell
        - task.git
      labels:
        environment: production
        trust_level: external
      limits:
        max_concurrency: 4
        timeout_seconds: 900
```

With this config, a job without `runtime_requirements`
is dispatched to `aee-lightweight-local` (the default);
a job with `required_capabilities: [task.git]` is
dispatched to `r-shell-prod-01`; a job with both
`required_capabilities: [task.shell]` AND
`required_labels: {environment: production}` is also
dispatched to `r-shell-prod-01`; a job with
`required_capabilities: [task.claude_code]` (which
neither Runtime advertises) fails with
`AEE_RUNTIME_NOT_FOUND` and the structured
`evaluated_runtimes` list.

See `docs/aee/AEE5_RUNTIME_REGISTRY_ARCHITECTURE.md`
§3 for the full selection algorithm.
